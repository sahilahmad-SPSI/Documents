Painting Rover — the seven changes that fix the straight line, and the tests that prove each one

Everything below uses only what is already on the rover: SCL3300 → Teensy 4.1 → Raspberry Pi 5 → 2× RoboClaw with wheel encoders. Both patch files are already written, delivered, and sitting in the project folder. This document is the execution order.

Companion to Straight-Line Path Investigation Patch files teensy_wall_heading_v2.ino · heading_control_v2.py (in CODE/) Date 12 August 2026

The blocker is no longer analysis — it is three numbers nobody has supplied and two hours of bench work nobody has scheduled. The hardware has a 29× accuracy margin over the job. Below: the fixes in execution order, the exact edit for each, and the one test that proves it worked.

Blocked until someone measures these three constants

They sit at the top of heading_control_v2.py with placeholder values. Wrong by 5% = overlap wrong by 5%.

ConstantPlaceholderHow to get the real value (15 min)
COUNTS_PER_REV1000Motion Studio: rotate one wheel exactly one turn by hand, read the encoder delta
WHEEL_DIAMETER_M0.100Roll the rover 10 wheel-turns on the floor along a tape measure; distance ÷ (10π). Measures the effective diameter on the magnets, not the catalogue one
TRACK_WIDTH_M0.400Tape measure, left wheel centre to right wheel centre

Also verify in Motion Studio that QPPS and the velocity PID are actually tuned on all four channels. The code calls SpeedM1M2 — velocity-PID mode — and a wrong QPPS saturates the loop into open-loop behaviour, silently.

Fix 1Send a signed heading, not the unsigned ANG_X registerstability
Replace CODE/Teensy Code/SCL3300_tilt_sensordata_send_ACS712_Relay.ino → with teensy_wall_heading_v2.ino (already in the folder)

getCalculatedAngleX() returns atan(acc_x / √(acc_y²+acc_z²)) — the denominator is a magnitude, so +2° and −2° of heading error read bit-identically. The steering loop cannot know which way to correct; in simulation it runs away in one direction.

Today (v1 firmware, line 104)

float x = inclinometer.getCalculatedAngleX();

v2 firmware

float a_f = SIGN_FORWARD * pickAxis(AXIS_FORWARD, ax, ay, az);
float a_l = SIGN_LATERAL * pickAxis(AXIS_LATERAL, ax, ay, az);
float phi = atan2f(a_l, a_f) * 57.2958f - heading_bias_deg;

Proves it: Test T1 below. Do not set AXIS_FORWARD/LATERAL by guessing — T1 identifies them empirically in 10 minutes.

Fix 2Put the SCL3300 in Mode 1 — it is currently outside its own datasheetvalidity + 4× less lag
Included in teensy_wall_heading_v2.ino → setup()

The Arduino library defaults to Mode 4 when setMode() is never called — and the v1 sketch never calls it. Murata limits Modes 3/4 to ±10° inclination; the rover sits at 90°. Mode 1 = ±1.2 g, 40 Hz filter (vs 10 Hz ≈ 16 ms of group delay).

inclinometer.setMode(1);      // BEFORE begin() — ±1.2 g, 6000 LSB/g, 40 Hz LPF
inclinometer.begin();
inclinometer.setFastReadMode();

The off-centre window alone is a permanent 436 mm one-sided bias — the first suspect if the rover always bows the same way. Proves it: T4 (re-square ≤ 0.3°, 10 times in a row).

Note sin(phi_actual) — the measured crab angle, not the nominal: at 30° a 3° turn error changes the lateral step by 9%. Also consider crabbing at 90° instead of 30°: same 150 mm step with zero height loss and no encoder-error amplification (30° costs 260 mm of height per step). This requires keeping packet serial — do not let anyone rewire the RoboClaws to RC/PWM mode. Proves it: T4 (step error ≤ ±5 mm, measured by tape and encoder readback).

Fix 6Add the integral term — P-only cannot cancel a constant pull349 mm → ~0
Straight mode_testing2.py lines 118–119, 462 → HeadingController.update() in heading_control_v2.py

Today

KP = 25
correction = int(KP * error)   # P only

Fixed

p = KP * err
if moving: i_term += KI * err * dt   # freeze at rest
i_term = clamp(i_term, ±MAX)          # anti-windup
corr = slew_limit(clamp(p + i_term, ±MAX))
if saturated: i_term = corr - p       # back-calc

With P-only, any constant disturbance (tether drag, off-centre gun, wheel mismatch) parks the loop at error = C/KP forever — a straight line at the wrong angle, which is the exact symptom. Start KI = KP/8 = 3. No D term until a gyro exists; differentiating the accelerometer angle is pure noise gain. Proves it: T3 (drag test: error returns to 0 within ~3 s).

Fix 7Latency housekeeping — about 10 lines and one Motion Studio setting90–320 → ~30–60 ms
Straight mode_testing2.py line 241 + tilt_reader() → AsyncLogger + HeadingSource in heading_control_v2.py
  • Move CSV logging off the sensor thread. _telemetry_csv_file.flush() currently runs inside tilt_reader() — an SD-card flush can stall the heading update 0–50 ms. Queue + writer thread.
  • Drain serial to the newest line: while ser.in_waiting > 64: line = ser.readline(). readline() returns the oldest buffered line, so a stall silently steers on stale data.
  • RoboClaw baud 38400 → 230400 in Motion Studio — the two blocking SpeedM1M2 calls currently cost ~5 ms of a 10 ms loop.
  • The v2 firmware timestamps every packet (H,seq,millis,…), so latency is now measured and logged as link_latency_ms instead of guessed.

Test ladder — each rung proves one fix before the next is trusted

Pass criteria stated before the tests, not after. T1–T3 are bench work; only T5 needs the wall. Total bench time: about half a day.

#TestProcedurePass criterionProves
T0
first, 20 min		 Baseline (do not skip) Before changing anything: chalk-line one pass with the current code and measure deviation every 1 m. Note whether the error is a consistent bow or a random wander. No pass/fail — this is the before-photo. Without it, nobody can say by how much the fixes helped, and a bow-vs-wander answer confirms which defect dominated. Baseline
T1
10 min		 Axis identification Flash v2 firmware. Send D. Hold the rover on the wall (or a vertical plate), rotate ~10° left then right about the surface normal. Watch phiXY / phiZY / phiXZ in the diagnostic stream. Exactly one combination gives a signed, linear ±10°; the old ANG_X gives the same number both ways. Set AXIS_FORWARD / AXIS_LATERAL + signs from the result. Fix 1, 2
T2
40 min		 Bias calibration + static log Rover held against a plumb line or laser-verified vertical. Send Z (500-sample average). Then leave untouched 30 min from cold, logging telemetry. After Z: heading reads 0.00 ± 0.05°. Over 30 min: noise ≤ 0.05° RMS, warm-up drift ≤ 0.10°. (Sensor spec says ~0.007° noise — large excess means a mounting or vibration problem, not a sensor problem.) Fix 3
T3
30 min		 Stands test: hold + disturbance rejection Rover on stands, wheels free, straight mode engaged at drive speed. (a) Tune KP: raise from 10 until the heading trace just overshoots, back off to 60%. (b) Add KI = KP/8. (c) Drag one side lightly by hand (simulated tether pull) for 10 s. (a) No sustained oscillation. (c) error_deg in the log returns to 0 within ~3 s while the drag is still applied — the visible signature of the integral term working. Fix 6, 7
T4
45 min		 Lane-change repeatability ×10 On stands or low on the wall: run 10 consecutive lane-change cycles. Mark chassis position before/after each step (tape measure) and record encoder readback + final heading from the log. Re-square: final heading ≤ ±0.3°, all 10 times. Step: achieved-vs-commanded ≤ ±5 mm on encoders and ≤ ±10 mm on tape (the difference between the two is slip, now measurable for the first time). Fix 4, 5
T5
1–2 h		 Chalk-line acceptance, on the wall Snap a plumb chalk line. Run one full pass up, lane change, one pass down, pump running. Measure deviation from the line every 1 m. Repeat 3×. ≤ 35 mm deviation over 10 m (0.20°), every pass, and the down-stripe parallel to the up-stripe within one overlap tolerance. This is the acceptance criterion for the whole work order. All

Expected end state, quantified

Noise floor 0.0068° (1.2 mm/10 m) + calibrated bias residual ≤ 0.05° (8.7 mm) + PI steady-state ≈ 0 + turn acceptance ≤ 0.3° at stripe start converging within the first metre  ⇒  ≤ 35 mm per 10 m pass is comfortably reachable with the sensors already fitted. The known residual risk is vibration corrupting the accelerometer while driving (accelerometers measure specific force, not gravity). T5 measures exactly that; only if it fails does the gyro question reopen — and both flight controllers the team already owns contain one.

Two standing cautions

  • Keep the RoboClaws on packet serial. Fix 5 depends on SpeedAccelDistanceM1M2 and encoder readback, which do not exist in RC/PWM mode. The parallel ArduRover proposal calls for RC mode — do not action that wiring change.
  • Hardware E-stop. 240 VAC rides the rover and every current stop path runs through Python. Fit a hardware motor-power cut before extended wall testing. Independent of every fix above.
