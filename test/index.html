Ground rules

  • Everything created today is test data — a second reset wipes it before the pilot.
  • All effective-from dates = the 1st of this month. All entries dated today. This is deliberate — a wrong effective date is the single most common way to get confusing zeros.
  • Job reference numbers will print MM-YY/TSJ-RA/01 and /02 — month, site code, vertical code, serial. The serial pool is shared per site+vertical+month, not per work order: that is why WO-2's first JR is /02, not /01.
  • "Refused" always means a named message or an absent control. A blank or raw error is always a ✗.
  • Checkbox state lives only in this open page — print or screenshot your tab before closing it.

How the data flows — what happens at each point

Ten stations. At each one: who acts, what gets created, and — the part that matters — what moves money and what does not.

ADM909Accounts & permissions Creating an account with a role auto-grants that role's permission template — nobody hand-assembles 26 checkboxes. Manual ticks are only for deltas (this test has exactly two: ₹ targets for Admin 2, Billed visibility for Management). Nothing about money exists yet.
ADM101Master data → a Draft package Location, client, vertical, the Client + Location pack with its code, the work order, its line items, their rates, and the stage weightages are all staged into one draft package per WO. Nothing here is live, nothing is visible downstream, no money exists — and the number of teams is not here at all: that is Admin 2's number now. The short codes (TSJ, RA) will be frozen forever by the first job reference that prints them.
ADM909Approvals (maker-checker) A package cannot even be submitted until it can price work — no line items, or a line item with no rate, and the Submit button is disabled with the reason written next to it. Once submitted, the checker can Return with remarks (package goes back, editable, resubmit becomes v2) or Approve (everything staged becomes live at once). The maker cannot approve their own package — the controls do not render for them. Approval is what makes a WO visible to Admin 2 and the validator. Still no revenue: a rate existing prices nothing by itself.
ADM201Wiring people to work Validator↔WO and supervisor↔validator mappings decide who may touch what (scope). Employee base + per-person points (L3 0.33 / L2 0.17 / L1 0.11 for Rope Access) + the number of teams (effective-dated — it can change mid-WO, and each work day uses the count in force that day) + std team definition (what one full team looks like) + per-day target (what one full team should produce). This creates the measuring stick — Fixed Target ₹ = target × teams-on-that-date × rate — but records no work. Until the team count is entered, screens say "team count not set", never a silent zero.
VAL201Job reference issued An official numbered permission to work: MM-YY/TSJ-RA/01. Issuing it freezes the codes inside it permanently. JRs are the unit that later gets closed and billed.
SUP301Daily entry — quantities only Permit number, per-stage quantities, named crew. The supervisor's screen carries no rupee anywhere — deliberately. Submitting creates a record awaiting validation and moves nothing: no report row, no dashboard tile, no target consumption. An unvalidated entry does not exist, financially.
VAL201Validation — the only gate where money is born Three powers: Return (goes back editable, resubmit increments revision — nothing moves), Reject (dead permanently — nothing moves, a fresh entry is needed), Approve — and only approve computes: Work Done Value = Σ(stage qty × rate × weightage), the day's stored result (prorated target from actual crew vs std team, efficiency %, points-per-person), and contract consumption. Rate used = the rate effective on the work date, forever — later rate changes never touch approved history.
VAL201Closure — measured truth Site measurement done, the validator closes the JR (partially or finally) with a measured ₹. This creates Actual (Unbilled) on the closure date and a closure accuracy row (measured vs what approvals had valued). Corrections stack with a reason and a flag — the original figure is never overwritten. A fully-closed JR disappears from the supervisor's entry picker.
ADM909Billed — the invoice fact Allowed only on a fully-closed JR, refused with a named message on open or partially-closed ones. Append-only with corrections, like closures. Gated by its own key (validation.billed_entry) — held by no role template except Super Admin; anyone else needs a manual grant even to see billed figures.
MGT001Dashboard & the five-row report Each row reads its own source and nothing is recomputed: Fixed Target ₹ and Calculated Target ₹ from the stored daily results · Work Done Value ₹ from approvals · Actual (Unbilled) ₹ from closure measurements · Billed ₹ from billed entries. Earned Revenue is a drill-down. Rows land on their own dates: targets & WDV on the work day, Actual on closure dates, Billed on the billed date.
