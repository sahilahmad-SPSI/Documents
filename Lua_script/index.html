What Lua scripting actually is here

A sandboxed Lua 5.3.6 interpreter running in its own RTOS thread inside the flight controller, with roughly 840 generated bindings into ArduPilot's C++ libraries. Scripts live as plain .lua files on the SD card. No firmware rebuild, no toolchain, no recompile to change behaviour in the field.

That is the pitch. The rest of this manual is mostly about the fine print, because the fine print is what decides whether a given R&D workstream belongs in Lua, in a C++ firmware fork, or on a companion computer.

Four constraints that decide everything

Read these before scoping any project. They are not edge cases , each one has killed real ArduPilot Lua work.

1 · Lowest priority thread in the firmware

SCR_THD_PRIORITY defaults to ChibiOS LOWPRIO — literally the lowest-priority thread ArduPilot creates. For scale, the main loop runs at 180, timer/RCOUT/SPI at 181. Every other subsystem preempts scripting. ArduPilot's own documentation states plainly that scripts are not guaranteed to be run on a reliable schedule.

2 · One Lua state, one heap, shared by all

There is no per-script memory quota. A script that leaks or over-allocates starves every other script on the vehicle. A full mark-and-sweep GC runs after every single script step, and collectgarbage() is not callable from Lua so you cannot control when.

3 · The binding surface is a hard ceiling

If a capability has no generated binding, no amount of Lua reaches it. Scripts cannot touch the attitude or rate inner loops, cannot see EKF internals, and cannot load native modules. Adding a binding means editing bindings.desc, regenerating, and owning a custom firmware build.

4 · Rover's surface is materially smaller than Copter's

No position controller, no scripted custom modes, no winch, no motor-matrix bindings, no precision-landing bindings. The ArduPilot wiki generates both vehicles' scripting pages from one shared source file, so it does not show this. The gating in bindings.desc does.

Streaming a velocity target with a watchdog

-- Guided velocity streaming at 10 Hz with an explicit staleness guard.
-- Adapted from examples/set-target-velocity.lua
local RATE_MS      = 100
local GUIDED       = 4
local STALE_MS     = 2000   -- our own budget, well under GUID_TIMEOUT (3000 ms)
local last_cmd_ms  = 0

function update()
  if vehicle:get_mode() ~= GUIDED then
    return update, RATE_MS                       -- idle politely, do not fight the pilot
  end

  local now = millis()
  local vel = Vector3f()
  vel:x(2.0)                                     -- 2 m/s north
  vel:y(0.0)
  vel:z(0.0)                                     -- NED: positive z is down

  if vehicle:set_target_velocity_NED(vel) then
    last_cmd_ms = now:toint()
  else
    gcs:send_text(3, "velocity target rejected")
  end

  if now:toint() - last_cmd_ms > STALE_MS then
    gcs:send_text(2, "guided stream stalled - releasing")
    vehicle:set_mode(5)                          -- LOITER: a safe place to fail to
  end

  return update, RATE_MS
end

return update, RATE_MS

Scripted custom flight modes

Limit · 4.7-dev onlyvehicle:register_custom_mode() is present on master / 4.7-dev and confirmed absent from the Copter-4.6.3 tag. It is in no released stable build as of August 2026. Do not design a product around it yet.

The mechanism registers a mode that behaves like Guided but reports its own number and name to the ground station via MAVLink AVAILABLE_MODES. Constraints, all verified in Copter.cpp:

  • A fixed pool of 5 slots (ModeGuidedCustom *mode_guided_custom[5]).
  • Mode numbers should be over 100. Colliding with a built-in mode returns nil.
  • Re-registering the same number and names — as happens after a scripting restart — returns the existing state object rather than erroring.
  • The returned custom_mode_state userdata exposes allow_entry() as a getter and setter, so a script can refuse entry conditionally.
  • Short name is capped at 4 characters.
-- Minimal scripted mode. Structure follows examples/Flip_Mode.lua,
-- which registers mode 100 and runs its control at 100 Hz.
local MODE_NUM = 101
local state = vehicle:register_custom_mode(MODE_NUM, "Survey Sweep", "SWEP")
if not state then
  gcs:send_text(3, "mode 101 registration failed")
  return                                          -- returning nothing stops this script cleanly
end

state:allow_entry(false)                          -- locked until preconditions are met

function update()
  local ready = arming:is_armed() and ahrs:healthy()
  state:allow_entry(ready)

  if vehicle:get_mode() == MODE_NUM then
    -- inside our mode we have the full Guided target surface
    local target = ahrs:get_location()
    if target then
      target:offset(10, 0)                       -- 10 m north
      vehicle:set_target_location(target)
    end
  end
  return update, 100
end

return update, 100

Missions & autonomy

NAV_SCRIPT_TIME is the supported way to hand bounded control to a script mid-mission. It works on Copter and Rover alike, and it is the right shape for almost all mission-embedded custom behaviour.

NAV_SCRIPT_TIME — MAV_CMD 42702

A mission item carrying a script-defined command byte, a timeout, and four arguments. The mission stalls at that item until the script says it is done or the timeout expires — whichever comes first.

Mission item fields
command 0–255 (meaning is yours), timeout seconds 0–255 with 0 meaning none, arg1–arg4.

Returns id, cmd, arg1, arg2, arg3, arg4, or all nil when no scripted item is active.

Tells the mission to advance. Pass back the same id you received.

Enables the scripting hook for a given mode.
-- Dispatcher for three scripted mission commands.
-- Adapted from examples/copter-nav-script-time.lua
local RATE_MS = 100
local active_id, started_ms = nil, 0

local handlers = {
  [1] = function(a1)                              -- cmd 1: hold and dwell a1 seconds
    return (millis():toint() - started_ms) > (a1 * 1000)
  end,
  [2] = function(a1)                              -- cmd 2: yaw to heading a1
    local loc = vehicle:get_target_location()
    if not loc then return true end            -- nothing to do, release the mission
    local err = math.abs(math.deg(ahrs:get_yaw_rad()) - a1)
    return err < 5.0
  end,
  [3] = function(a1, a2)                          -- cmd 3: pulse a payload servo
    SRV_Channels:set_output_pwm_chan_timeout(0, a1, 500)
    return (millis():toint() - started_ms) > (a2 * 1000)
  end,
}

function update()
  local id, cmd, a1, a2 = vehicle:nav_script_time()

  if not id then
    active_id = nil
    return update, RATE_MS
  end

  if id ~= active_id then                          -- newly entered item
    active_id, started_ms = id, millis():toint()
    gcs:send_text(6, string.format("scripted cmd %d begin", cmd))
  end

  local h = handlers[cmd]
  if not h then
    gcs:send_text(4, string.format("unknown scripted cmd %d", cmd))
    vehicle:nav_script_time_done(id)              -- never strand the mission
  elseif h(a1, a2) then
    vehicle:nav_script_time_done(id)
  end

  return update, RATE_MS
end

return update, RATE_MS
Limit · the timeout raceThe mission advances on whichever comes first: your nav_script_time_done() or the item's own timeout. Set the item timeout generously longer than your expected completion so your logic resolves the step, not the timeout cutting it off mid-action. A timeout of 0 disables it — which also means a bug in your handler strands the mission forever.

Serial rangefinder driver skeleton

-- Feed a serial distance sensor into ArduPilot's rangefinder subsystem.
-- Requires SERIALx_PROTOCOL = 28 and RNGFNDn_TYPE = 36, then reboot.
local RATE_MS   = 50          -- 20 Hz
local BAUD      = 115200
local INSTANCE  = 0
local TIMEOUT_MS= 1000

local port = serial:find_serial(0)
local rf   = rangefinder:get_backend(INSTANCE)

if not port then gcs:send_text(3, "no scripting serial port") return end
if not rf   then gcs:send_text(3, "no scripting rangefinder backend") return end
port:begin(BAUD)
port:set_flow_control(0)

local buf, last_good = "", millis():toint()

function update()
  local n = port:available():toint()
  if n > 0 then
    buf = buf .. port:readstring(n)         -- one binding call, not a byte loop
  end

  -- frame: 0x59 0x59 <lo> <hi> <strength_lo> <strength_hi> ... <checksum>
  while #buf >= 9 do
    local i = buf:find("\x59\x59", 1, true)
    if not i then buf = "" break end
    if #buf < i + 8 then buf = buf:sub(i) break end

    local frame = buf:sub(i, i + 8)
    buf = buf:sub(i + 9)

    local sum = 0
    for b = 1, 8 do sum = sum + frame:byte(b) end
    if (sum & 0xFF) == frame:byte(9) then
      local cm = string.unpack("<I2", frame, 3)
      rf:handle_script_msg(cm * 0.01)          -- metres
      last_good = millis():toint()
    end
  end

  if millis():toint() - last_good > TIMEOUT_MS then
    gcs:send_text(4, "rangefinder silent")
    last_good = millis():toint()               -- rate-limit the nagging
  end

  return update, RATE_MS
end

return update, RATE_MS

Locking down a production airframe

Checksum lockdownSCR_LD_CHECKSUM and SCR_RUN_CHECKSUM hold an XOR of CRC32 across all loaded and all running scripts; a mismatch blocks arming. Set SCR_DEBUG_OPTS bit 5 once with the correct scripts running and the firmware computes and saves both values, then clears the bit. This catches an ejected SD card, a corrupted file, or a run-once script that failed to exit. Both parameters default to -1 (disabled) and were added in 4.5.
HazardSCR_DEBUG_OPTS bit 4 disables the scripting pre-arm check entirely. It is a development convenience. Shipping with it set means a script that failed to load no longer stops you arming.

Vehicle control & drive modes

Rover gives a script two distinct levels of control: high-level speed and turn-rate demands that leave ArduPilot's controllers in charge, and direct steering/throttle override that takes them out of the loop entirely. Choose deliberately — the second one makes your Lua script the controller, at Lua's rate and Lua's priority.

The two control levels

Level 1 — command the controllers

set_desired_speed(m_s) and set_desired_turn_rate_and_speed(deg_s, m_s). ArduPilot's speed and steering controllers still run, still respect their tuning, still slew-limit. Safe at 10 Hz. This is the right default.

Level 2 — own the actuators

set_steering_and_throttle(steer, throttle), both normalised. The controllers are bypassed. You are now responsible for rate limiting, sign conventions and stopping. Needs 50–100 Hz and a watchdog.

Limit · output latchRover latches the last scripted steering/throttle values. If your script stops updating them the vehicle keeps driving on the stale demand until the mode changes or the Guided timeout intervenes. Build an explicit staleness check into every script that uses level 2 — this is the single most dangerous pattern on a ground vehicle that shares space with people.

Custom drive mixer — the flagship Rover capability

examples/rover-motor-driver.lua is ArduPilot's own reference: it reads the controller's throttle and steering demand at 100 Hz, applies Ackermann mixing in Lua, and writes two scripting servo outputs. Everything upstream — navigation, speed control, failsafes — keeps working.

-- Skid-steer differential mixer sitting downstream of ArduPilot's controllers.
-- Structure adapted from examples/rover-motor-driver.lua (100 Hz).
local RATE_MS   = 10
local LEFT_CHAN = 0          -- SERVO_FUNCTION 94  "Script Out 1"
local RIGHT_CHAN= 1          -- SERVO_FUNCTION 95  "Script Out 2"
local PWM_MID   = 1500
local PWM_SPAN  = 400
local HOLD_MS   = 100        -- outputs revert if we stop writing

local function clamp(v, lo, hi)
  if v < lo then return lo elseif v > hi then return hi end
  return v
end

function update()
  local thr   = vehicle:get_control_output(3)   -- Throttle, -1..1
  local steer = vehicle:get_control_output(4)   -- Yaw,      -1..1

  if not thr or not steer or not arming:is_armed() then
    return update, RATE_MS                      -- write nothing; outputs time out safely
  end

  local left  = clamp(thr + steer, -1, 1)
  local right = clamp(thr - steer, -1, 1)

  SRV_Channels:set_output_pwm_chan_timeout(LEFT_CHAN,
      math.floor(PWM_MID + left  * PWM_SPAN), HOLD_MS)
  SRV_Channels:set_output_pwm_chan_timeout(RIGHT_CHAN,
      math.floor(PWM_MID + right * PWM_SPAN), HOLD_MS)

  return update, RATE_MS
end

return update, RATE_MS
Why this pattern is goodWriting nothing when disarmed or when a read returns nil, combined with the _timeout variant, means a crashed script produces a stopped vehicle rather than a runaway one. Never use the non-timeout setters for drive outputs.

No custom modes — three alternatives

Rover has no register_custom_mode(). The viable substitutes, in decreasing order of how well they behave:

  1. Guided plus streamed targets. Put the vehicle in GUIDED (15) and stream set_target_location or set_target_velocity_NED. ArduPilot keeps its failsafes and mode-change logic. This is the closest analogue to a custom mode and the one to reach for first.
  2. An aux-switch behaviour layer. Assign an RCx_OPTION in the 300–315 range and have your script overlay behaviour on whatever mode is active — adjusting speed, gating on obstacles, driving a payload. The operator keeps a physical way to disengage you.
  3. Level-2 actuator override. Take the actuators with set_steering_and_throttle(). Maximum freedom, maximum responsibility, and the one that most deserves a hardware e-stop wired independently of the autopilot.

Obstacle-gated speed — the archetypal Rover script

-- Scale AUTO speed by the nearest obstacle, with a full stop inside a hard limit.
-- Uses proximity:get_closest_object(), which returns angle_deg, distance_m.
local RATE_MS    = 100
local AUTO       = 10
local HOLD       = 4
local STOP_M     = 1.0
local SLOW_M     = 6.0
local SPEED_MAX  = 2.0
local SPEED_MIN  = 0.3
local FWD_ARC    = 60          -- only care about +/- 60 deg ahead

function update()
  if vehicle:get_mode() ~= AUTO then
    return update, RATE_MS
  end

  local angle, dist = proximity:get_closest_object()
  if not dist then
    return update, RATE_MS                 -- no proximity data: do not interfere
  end

  -- ignore anything outside the forward arc
  local a = math.abs(((angle + 180) % 360) - 180)
  if a > FWD_ARC then
    vehicle:set_desired_speed(SPEED_MAX)
    return update, RATE_MS
  end

  if dist <= STOP_M then
    gcs:send_text(2, string.format("obstacle %.1fm - holding", dist))
    vehicle:set_mode(HOLD)
  elseif dist < SLOW_M then
    local frac  = (dist - STOP_M) / (SLOW_M - STOP_M)
    local speed = SPEED_MIN + frac * (SPEED_MAX - SPEED_MIN)
    vehicle:set_desired_speed(speed)
  else
    vehicle:set_desired_speed(SPEED_MAX)
  end

  return update, RATE_MS
end

return update, RATE_MS

Missions & autonomy

The mission API is identical to Copter's, and NAV_SCRIPT_TIME works — Rover overrides nav_script_time, nav_script_time_done and nav_scripting_enable. For a ground robot this is how you get “stop here, do a thing, carry on” into a survey route.

Rover implementation detailRover services a NAV_SCRIPT_TIME item by entering a Guided sub-mode internally. If Guided entry fails, the item is skipped rather than stalling the mission — different from Copter, and worth knowing when a scripted step silently does nothing.

Scripted mission step: stop, sample, resume

-- NAV_SCRIPT_TIME handler for a soil-sampling rover.
-- cmd 1 = deploy probe for arg1 seconds, then retract.
local RATE_MS   = 100
local PROBE_CH  = 0        -- SERVO_FUNCTION 94
local PWM_DOWN  = 1900
local PWM_UP    = 1100

local ST_IDLE, ST_STOP, ST_DOWN, ST_DWELL, ST_UP = 0, 1, 2, 3, 4
local st, st_ms, cur_id = ST_IDLE, 0, nil

local function enter(s)
  st, st_ms = s, millis():toint()
end

local function held(ms)
  return (millis():toint() - st_ms) >= ms
end

function update()
  local id, cmd, a1 = vehicle:nav_script_time()

  if not id then
    if st ~= ST_IDLE then enter(ST_IDLE) end
    cur_id = nil
    return update, RATE_MS
  end

  if id ~= cur_id then
    cur_id = id
    if cmd == 1 then enter(ST_STOP) else vehicle:nav_script_time_done(id) end
  end

  if st == ST_STOP then
    vehicle:set_desired_speed(0)
    if held(1500) then enter(ST_DOWN) end

  elseif st == ST_DOWN then
    SRV_Channels:set_output_pwm_chan_timeout(PROBE_CH, PWM_DOWN, 200)
    if held(2000) then enter(ST_DWELL) end

  elseif st == ST_DWELL then
    SRV_Channels:set_output_pwm_chan_timeout(PROBE_CH, PWM_DOWN, 200)
    if held((a1 or 5) * 1000) then enter(ST_UP) end

  elseif st == ST_UP then
    SRV_Channels:set_output_pwm_chan_timeout(PROBE_CH, PWM_UP, 200)
    if held(2000) then
      logger:write("SMPL", "Id,Dwell", "if", "--", "--", id, a1 or 5)
      vehicle:nav_script_time_done(id)
      enter(ST_IDLE)
    end
  end

  return update, RATE_MS
end

return update, RATE_MS
Why a state machine and not a wait loopLua has no coroutines in ArduPilot — the coroutine library is not loaded at all. There is no yield. Every multi-step sequence has to be an explicit state machine spread across successive scheduled calls, exactly as above. Blocking inside update() blocks every other script on the vehicle and will trip SCR_VM_I_COUNT.

      gcs:send_text(2, "GCS link lost - holding")

Power, battery, EFI, generator

The battery, efi and relay surfaces are identical to Copter's. What changes on a rover is the duty cycle: long runs at modest, fairly steady current make state-of-charge estimation and range prediction genuinely tractable in a way they are not on a multirotor.

Range estimation from consumption

-- Estimate remaining range and warn before it becomes a recovery problem.
local RATE_MS  = 2000
local RESERVE  = 0.20        -- keep 20% in hand
local warned   = false

function update()
  local used = battery:consumed_mah(0)
  local pct  = battery:capacity_remaining_pct(0)
  local home = ahrs:get_home()
  local here = ahrs:get_location()

  if not (used and pct and home and here) or used < 50 then
    return update, RATE_MS               -- not enough signal yet
  end

  local dist_home = here:get_distance(home)
  local travelled = math.max(dist_home, 1)
  local mah_per_m  = used / travelled
  local usable_pct = math.max(pct / 100 - RESERVE, 0)
  local total_mah  = used / math.max(1 - pct / 100, 0.01)
  local range_m    = (total_mah * usable_pct) / math.max(mah_per_m, 0.001)

  logger:write("RNGE", "Est,DHome,Pct", "fff", "m m %", "---",
               range_m, dist_home, pct)

  if range_m < dist_home and not warned then
    gcs:send_text(2, string.format(
      "range %.0fm below distance home %.0fm", range_m, dist_home))
    warned = true
  end

  return update, RATE_MS
end

return update, RATE_MS

Straight-line distance is a floor, not the route length — treat the estimate as a warning trigger, not a guarantee.

Safety, failsafe, arming, fence

A ground robot shares space with people in a way an aircraft usually does not. This section is where the low-priority-thread caveat stops being an engineering footnote and starts being a safety argument.

What Lua should and should not be trusted with

Reasonable in Lua

Arming gates via the aux-auth API. Speed limiting by zone or obstacle distance. Health monitoring and alerting. Fence-breach early warning. Mission pause and resume. Logging and diagnostics. Anything where being late by 200 ms degrades performance rather than causing harm.

Not safe as the only layer

Emergency stop. Collision avoidance of last resort. Anything a person's safety depends on. These need ArduPilot's own C++ failsafes, a hardware e-stop wired independently of the autopilot, or both. A Lua script can be preempted, can be removed by an instruction-budget overrun, and can be starved of heap by an unrelated script.

Arming gates

The aux-auth mechanism — arming:get_aux_auth_id(), then set_aux_auth_failed(id, msg) or set_aux_auth_passed(id) — is the supported path. examples/rover-MinFixType.lua is a real Rover example of gating on GPS fix type. See the Copter tab for a complete worked pattern; it is identical here.

Fence

CorrectionThere is no fence:get_action() and no fence:enabled(). The real surface is fence:get_breaches(), fence:get_breach_time(), fence:get_enabled_fences() and fence:present().

Polygon fences and exclusion zones matter more on a rover than on a copter, because the consequence of leaving one is usually a road or a drop rather than open air. A script can read breaches and add pre-breach slowing, but the enforcement stays in C++ where it belongs.

Failure detection

vehicle:is_crashed()
Rover-only crash detector. Use it to trigger a scripted safe state.
vehicle:has_ekf_failsafed()
Not implemented on Rover — always returns false. Use ahrs:healthy(), ahrs:get_variances() and gps:status() instead.
AR_AttitudeControl:get_srate()
Persistently saturated slew rates are a good stuck-vehicle or lost-traction indicator.
rc:has_valid_input() / gcs:last_seen()
Link-loss detection, as a second layer behind ArduPilot's failsafes.
SRV_Channels:get_safety_state()
Safety switch. Never drive outputs against it.

Pre-deployment checklist

  1. Every actuator write uses set_output_pwm_chan_timeout(), never the latching variant.
  2. Every binding that can return nil is checked before use.
  3. update() is wrapped in pcall with an error backoff, so one bad frame does not remove the script.
  4. There is a defined safe state and every failure path reaches it — usually mode HOLD plus zeroed steering and throttle.
  5. A hardware e-stop exists that does not depend on the autopilot running.
  6. SCR_LD_CHECKSUM and SCR_RUN_CHECKSUM are snapshotted so the vehicle refuses to arm if the scripts on the card change.
  7. SCR_DEBUG_OPTS bit 4 is clear, so the scripting pre-arm check is active.
  8. Heap headroom has been measured with SCR_DEBUG_OPTS bit 1 under worst-case load, not just at idle.

-- Map vehicle state to a light pattern, with an audible warning before movement.
local RATE_MS = 100
local CHAN    = 0          -- serialLED on Script Out 1
local NLEDS   = 12

serialLED:set_num_neopixel(CHAN, NLEDS)

local function fill(r, g, b)
  serialLED:set_RGB(CHAN, -1, r, g, b)   -- -1 addresses every LED
  serialLED:send(CHAN)                    -- nothing lights up without this
end

function update()
  local armed = arming:is_armed()
  local mode  = vehicle:get_mode()
  phase = (phase + 1) % 20

  if armed and not was_armed then
    notify:play_tune("MFT200L4CDE")         -- audible pre-move warning
    warn_ms = millis():toint()
  end
  was_armed = armed

  if not armed then
    fill(0, 40, 0)                          -- steady green: safe to approach
  elseif mode == AUTO then
    local on = phase < 10
    fill(on and 255 or 40, on and 140 or 20, 0)  -- flashing amber: autonomous
  elseif mode == HOLD then
    fill(120, 60, 0)                        -- steady amber: armed but stopped
  else
    fill(0, 0, 120)                          -- blue: under manual control
  end

  return update, RATE_MS
end

Memory

Two separate pools, and only one of them is tunable.

C stack — not tunable

The scripting thread's stack is a build-time constant: default 17 KB, hard floor 8 KB via static_assert, ceiling 64 KB. No SCR_* parameter reaches it. The source comment notes Linux corrupts its stack around 16.25 KB when handed bad scripts.

Lua heap — SCR_HEAP_SIZE

A dedicated AP_MultiHeap, not the system heap, able to span up to 10 discontiguous regions with 20 KB of system RAM permanently reserved and never consumed.

Default heap size is tiered by board

204,800 bytes
SITL, Linux, or HAL_MEM_CLASS ≥ 1000.
102,400 bytes
HAL_MEM_CLASS ≥ 500.
44,032 bytes
Everything else. Some shipped applets need 300 KB — on a constrained board you will be raising this.

To free RAM on a tight board: SRTL_POINTS=0, TERRAIN_ENABLE=0, INS_LOG_BAT_MASK=0, reduce LOG_FILE_BUFSIZE (not below 16 KB without log gaps), reduce CAN_Dx_UC_POOL.

The out-of-memory sequence, exactly as implemented

  1. Allocation fails in all existing regions. If this is the first consecutive failure it is recorded and returned immediately — deliberately, to give Lua's GC a chance before anything drastic happens.
  2. On a second consecutive failure, if disarmed: no expansion is attempted at all. The source comment says plainly that the user should fix their SCR_HEAP_SIZE.
  3. If armed, free system RAM covers 20 KB reserve plus the request, and fewer than 10 regions are in use: a new region of at least 30 KB is taken from the system pool and a one-time GCS warning is printed — Scripting: Required SCR_HEAP_SIZE over <N>.
  4. If that still fails, Lua raises its normal OOM error, the per-script pcall catches it, and only that one script is unloaded.
Version noteThis expand-and-warn behaviour is verifiably present in the Copter-4.6.0 tag and absent from 4.5.0. The wiki attributes it to "4.7 and later". The source is correct.
Engine-level failureIf the initial heap cannot be created at engine start, the whole engine never launches: the GCS gets Scripting: Unable to allocate memory and the pre-arm check reads Scripting: out of memory.

Measuring your script's cost

Set SCR_DEBUG_OPTS bit 1 and the engine emits Lua: Time: <us> Mem: <total> + <delta> after each step. The delta is that step's allocation — the number you budget against. Bit 3 routes it to dataflash for a long run. Set bit 6 to disable auto-expansion while sizing, so under-provisioning fails loudly instead of silently growing.

Hidden cost · requireArduPilot's require is modified so each script gets its own _LOADED table. Every script that requires a module pays for its own copy of it. Modules also cannot be used to share state between scripts — each sees a private instance.

CPU and scheduling

SCR_VM_I_COUNT is an instruction budget

A LUA_MASKCOUNT debug hook is re-armed at the start of every call into a script. If it fires mid-call it immediately re-arms at count 1 — to bail out even inside error handlers — and raises Exceeded CPU time. The scheduler reports <script> exceeded time limit and removes that script from the run queue permanently.

Default is 10,000 instructions, range 1,000–1,000,000, and the value is clamped with MAX(steps, 1000) so you cannot go lower than 1,000 in practice. Because it counts instructions rather than time, a single binding call is one instruction regardless of how long the underlying C++ takes. That cuts both ways: port:readstring(512) is cheap in budget terms, while a 512-iteration byte loop is not.

The scheduling model

  • One dedicated RTOS thread named Scripting. It is not a task in AP_Scheduler's fixed-rate main-loop table, so there is no "Hz slot" for it.
  • Inside the engine, scheduling is cooperative and non-preemptive between scripts: a sorted linked list ordered by next_run_ms, soonest-due runs to completion first. One heavy script blocks all the others.
  • Idle sleeps are chunked to at most 65,535 ms, so in the pathological case a restart request can take up to ~65 seconds to be noticed. An empty script list sleeps in 1-second increments.
  • ArduPilot's own wording: scripts are not guaranteed to be run on a reliable schedule.

Numeric precision

docs.lua states it directly: lua ints are 32 bits and lua floats will loose resolution at large values. Single precision gives exact integers only to 224 = 16,777,216, roughly 6–7 significant decimal digits.

millis() / micros()

Both return boxed uint32_t_ud. micros() wraps every ~71.6 minutes; millis() every ~49.7 days. Never accumulate either into a plain float.

Location lat / lng

Integer degrees × 1e7, deliberately. Converting to float degrees and differencing loses about a metre around the 5th–6th decimal place.

Script parameters

param:add_table() creates float-only parameters. No int8, int16 or boolean types are available to a script.

-- Wrong: float accumulation and float-degree differencing.
local t = millis():tofloat()          -- loses ms resolution after ~4.6 hours
local dlat = (a:lat() - b:lat()) / 1e7  -- ~1 m error at typical latitudes

-- Right: stay in boxed integers and use the C++ helpers.
local t = millis():toint()            -- integer ms, wraps predictably
local d = a:get_distance(b)            -- metres, computed in double precision in C++

Getting scripts running

Set SCR_ENABLE = 1, reboot, drop .lua files in APM/scripts on the SD card, reboot again. That is the whole happy path. Everything below is what to do when it does not work.

Where scripts are loaded from

APM/scripts
The SD card directory, created automatically the first time SCR_ENABLE=1 survives a reboot. This is the normal location on real hardware.
@ROMFS/scripts
Baked into the firmware image. Used by OEMs shipping scripts as part of a product.
./scripts
In SITL, relative to the directory sim_vehicle.py was launched from.

Only files ending in .lua and not starting with . are loaded, in directory read order. SCR_DIR_DISABLE is a bitmask that switches off either source: bit 0 disables ROMFS, bit 1 disables APM/scripts.

The scheduling contract

Every script's top-level chunk, and every callback it returns, must return a function and a delay in milliseconds. This is the entire scheduling interface.

-- The minimum viable script.
function update()
  gcs:send_text(6, "still here")
  return update, 1000        -- run me again in 1000 ms
end

return update, 1000            -- and start me in 1000 ms

Returning nothing ends that script cleanly — the idiom for run-once initialisation. Getting the contract wrong produces one of three specific errors: did not return a function, did not return a delay, or returned bad result count.

Restarting without a reboot

Critical · no auto-reloadIf the Lua VM exits — a crash, a panic, an out-of-memory at start — the scripting thread does not reload. It drops into a 1 Hz polling loop and waits. Nothing happens until one of the restart paths below fires.
  • scripting:restart_all() from Lua.
  • An RC aux switch set to RCx_OPTION = 316.
  • MAVLink MAV_CMD_SCRIPTING (42701) with sub-command 2 (stop) or 3 (stop and restart).
  • Cycling SCR_ENABLE from 0 back to 1 — any other value change is a no-op.
  • A full reboot.
  • In SITL, scripting restart at the MAVProxy prompt — hot-reloads edited files without restarting the simulator.

Failure containment

Script-level failure

A runtime error, an OOM, or an instruction overrun in one script removes only that script. The engine and every other script keep running. A pre-arm failure is raised if it happened before arming.

Engine-level failure

A failed initial heap or state allocation, or an error escaping the top-level protected call, tears down the entire engine. All scripts stop, and nothing auto-reloads.

Production script skeleton

Every applet worth shipping has roughly this shape: a parameter table, a protected update, an error backoff, and no assumption that any binding returns what you expect.

-- Production skeleton. Adapted from examples/protected_call.lua
-- and the structure common to applets/ scripts.
local SCRIPT_NAME = "myapp"
local RATE_MS     = 100
local ERR_BACKOFF = 3000

local PARAM_TABLE_KEY, PREFIX = 73, "MYAPP_"
assert(param:add_table(PARAM_TABLE_KEY, PREFIX, 2), "param table failed")
local function bind(name, idx, default)
  assert(param:add_param(PARAM_TABLE_KEY, idx, name, default))
  return Parameter(PREFIX .. name)
end
local P_ENABLE = bind("ENABLE", 1, 0)
local P_RATE   = bind("RATE",   2, 1.0)

local state = { last_ms = 0, count = 0 }

local function update()
  if P_ENABLE:get() < 1 then return end       -- cheap disabled path

  local loc = ahrs:get_location()
  if not loc then return end                    -- nil-check every optional return

  state.count = state.count + 1
  -- ... real work ...
end

-- The wrapper is what keeps one bad frame from removing the script.
local function protected()
  local ok, err = pcall(update)
  if not ok then
    gcs:send_text(3, SCRIPT_NAME .. ": " .. tostring(err))
    return protected, ERR_BACKOFF          -- slow down, do not spin on the error
  end
  return protected, RATE_MS
end

gcs:send_text(5, SCRIPT_NAME .. " loaded")
return protected, RATE_MS
Why pcall mattersWithout it, a single runtime error — a nil arithmetic, a bad index — removes the script permanently until a manual restart. With it, the script survives a transient and tells you about it.

Time, state machines and scheduling

Boxed integer time

-- millis() and micros() both return uint32_t_ud, not plain numbers.
local now_ms = millis():toint()      -- integer, safe for differencing
local now_us = micros():toint()      -- wraps every ~71.6 minutes

-- Wrap-safe elapsed check. Unsigned arithmetic makes the subtraction
-- correct across a wrap, provided you never convert to float first.
local function elapsed(since_ms, window_ms)
  return (millis():toint() - since_ms) >= window_ms
end

-- Wall-clock time, when you actually need a date, comes from rtc:
local ms_since_epoch = rtc:get_utc_usec()

State machine — the coroutine replacement

-- There is no coroutine library. Multi-step sequences are explicit states
-- with a per-state timeout guard, advanced across scheduled calls.
local S = { IDLE = 0, ARM = 1, RUN = 2, DONE = 3, FAIL = 4 }
local TIMEOUTS = { [S.ARM] = 5000, [S.RUN] = 30000 }

local st, st_ms = S.IDLE, 0

local function goto_state(s)
  st, st_ms = s, millis():toint()
end

local function timed_out()
  local limit = TIMEOUTS[st]
  return limit and (millis():toint() - st_ms) > limit
end

function update()
  if timed_out() then
    gcs:send_text(3, "sequence timed out in state " .. st)
    goto_state(S.FAIL)
  end

  if st == S.IDLE then
    if rc:get_aux_cached(300) == 2 then goto_state(S.ARM) end
  elseif st == S.ARM then
    if arming:is_armed() then goto_state(S.RUN) end
  elseif st == S.RUN then
    -- do the work; call goto_state(S.DONE) when finished
  elseif st == S.FAIL then
    goto_state(S.IDLE)
  end

  return update, 100
end

return update, 100

Variable-rate scheduling

-- The delay you return can change every call. Spend instructions where
-- they matter and idle cheaply everywhere else.
function update()
  if not arming:is_armed() then
    return update, 1000            -- 1 Hz on the ground
  end
  if vehicle:get_mode() ~= 4 then
    return update, 200             -- 5 Hz when not our mode
  end
  -- active control path
  return update, 20                -- 50 Hz only when it counts
end

-- Raw CAN. Adapted from examples/CAN_read.lua and CAN_write.lua.
local driver = CAN:get_device(10)          -- 10-frame receive buffer
if not driver then gcs:send_text(3, "no scripting CAN bus") return end

local TARGET_ID = 0x123

function update()
  -- receive: drain the buffer every call, do not let it overflow
  while true do
    local frame = driver:read_frame()
    if not frame then break end
    if frame:id() == TARGET_ID then
      local rpm = (frame:data(0) << 8) | frame:data(1)
      esc_telem:update_rpm(0, rpm, 0)
    end
  end

  -- transmit
  local out = CANFrame()
  out:id(0x200)
  out:dlc(2)
  out:data(0, 0xAA)
  out:data(1, 0x55)
  driver:write_frame(out, 10000)          -- 10 ms timeout, microseconds

  return update, 20
end

Aux switches

-- rc:get_aux_cached() returns 0 (low), 1 (middle), 2 (high), or nil.
-- Cached means it does not block; adapted from examples/aux_cached.lua.
local AUX_FN = 300                        -- RCx_OPTION = 300  "Scripting1"
local last_pos, stable_ms = nil, 0
local DEBOUNCE_MS = 200

function update()
  local pos = rc:get_aux_cached(AUX_FN)

  if pos ~= last_pos then
    last_pos, stable_ms = pos, millis():toint()
  elseif pos and (millis():toint() - stable_ms) == DEBOUNCE_MS then
    -- fires once, DEBOUNCE_MS after the switch settles
    gcs:send_text(6, "aux switch now " .. pos)
  end

  return update, 50
end

return update, 50

Custom log messages

-- logger:write(name, labels, format, units, multipliers, ...)
--   name       <= 4 chars
--   labels     < 58 chars total
--   format     < 15 chars, so at most 14 fields
--   valid fmt  b h c H C Q Z i I f n N B e E L M   (NOT d q a)
function update()
  local v = battery:voltage(0) or 0
  local a = battery:current_amps(0) or 0
  local n = gps:num_sats(0)

  logger:write("PWR1",          -- message name
               "Volt,Amp,Sats", -- labels
               "ffB",           -- float, float, uint8
               "vA-",           -- units: volts, amps, none
               "---",           -- multipliers: none
               v, a, n)
  return update, 200
end

return update, 200

One script, both vehicles

-- FWVersion:type(): 1 Rover, 2 ArduCopter, 3 Plane, 4 Tracker,
--                   7 Sub, 9 AP_Periph, 12 Blimp, 13 Heli
local VEH = FWVersion:type()
local IS_COPTER = (VEH == 2 or VEH == 13)
local IS_ROVER  = (VEH == 1)

local function stop()
  if IS_ROVER then
    vehicle:set_steering_and_throttle(0, 0)
    vehicle:set_mode(4)                      -- Rover HOLD
  elseif IS_COPTER then
    vehicle:set_mode(5)                      -- Copter LOITER
  end
end

Memory discipline

-- Allocate once, reuse forever. Every table and userdata created inside
-- update() is garbage the next GC pass has to walk.
local scratch_vec = Vector3f()          -- reused, not recreated
local parts = {}                        -- reused buffer table

function update()
  scratch_vec:x(1.0)
  scratch_vec:y(0.0)
  scratch_vec:z(0.0)
  vehicle:set_target_velocity_NED(scratch_vec)

  -- Build strings with table.concat, never with .. in a loop.
  for i = 1, 8 do parts[i] = tostring(i) end
  local line = table.concat(parts, ",")

  return update, 50
end

return update, 50
Watch forLocation, Vector3f and friends are userdata — plain assignment shares the object. Use :copy() when you need an independent value, or you will mutate something you did not mean to.

Blocking arming from a script

-- The aux-auth API is the supported way. Adapted from applets/arming-checks.lua.
local auth_id = arming:get_aux_auth_id()
if not auth_id then return end

function update()
  local sats = gps:num_sats(0)
  if not sats or sats < 12 then
    arming:set_aux_auth_failed(auth_id,
      string.format("need 12 sats, have %d", sats or 0))
  else
    arming:set_aux_auth_passed(auth_id)
  end
  return update, 1000
end

return update, 1000
